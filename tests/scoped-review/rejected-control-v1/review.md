**Signal Desk feels calm and legible, but its inspection and preview actions need attention before release.** This is a production-close operations queue. Staff likely arrive scanning for work that needs a response; misleading feedback costs time and confidence in what they have reviewed.

**First impressions.** The desktop screen establishes a clear sequence: page title, requests, then supporting guidance and reply preview. Bordered panels, neutral controls and green/amber status labels form a coherent language. The shadowed help surface has a distinct floating role. Mobile retains readable content and reachable controls, though the narrow table makes both request names and “Open request” wrap.

**Inspection stops before the useful information.** Both request buttons open the same generic dialog body: “The request is ready for review.” Only the title changes. A Waiting request therefore opens without explaining what it needs or showing its request content. This is the highest-impact gap: the user can identify work but cannot meaningfully inspect it. Populate the dialog with the request details and its actual status, including the reply requirement for waiting work. The supplied source establishes this behavior; no dialog capture was provided. (`case-17.html:1`)

**“Preview reply” promises content but produces a status message.** Its handler only writes “Preview ready: North wing access.” into the status region inside the Requests panel. It neither reveals reply text nor opens a preview. On mobile, that feedback is above the preview control and can be outside the current viewport, leaving the user uncertain whether anything happened. Show the actual reply beside the trigger or in a clearly titled dialog, with feedback local to that interaction. This is a Transparency issue with a concrete functional consequence: the user cannot check the reply. (`case-17.html:1`)

**Export scope needs to be explicit.** Waiting visibly hides North wing access, but the CSV handler always exports both requests. Exporting the entire queue may be intentional; the current “Export CSV” label does not establish that distinction. If full-queue export is the requirement, label it “Export all requests.” If export should follow the filter, generate it from the visible subset. Either approach prevents staff from discovering the scope only after opening the file. (`case-17.html:1`)

**Mobile preserves access, with some avoidable scanning friction.** The receipt confirms a 390px document width at a 390px viewport, and the bottom capture shows the preview button fully inside its panel. There is no demonstrated horizontal-overflow problem. The toolbar does push Export onto a separate row, while the table’s action labels occupy two lines. A deliberate mobile toolbar grouping and more room for request actions would make repeated scanning smoother without changing the product direction.

**Craft worth keeping.** The source uses three explicit type sizes, 16/18/28px, and three explicit weights, 400/600/700, with inherited bold for the preview label. Four neutral text colors plus green, amber and white serve distinct roles. The system font fits an operational tool; heading hierarchy, short reading measure and text-group rhythm hold across the captures. Status words supplement color. Native buttons, column headers, pressed filter states and visible focus styling provide useful foundations. Waiting also retains the queue owner, as both source and measurements confirm.

**Top opportunities.** Complete request inspection first, make reply preview display the promised content, then clarify export scope. Those changes address the moments where a rushed operator needs certainty. The visual system can support them as it stands.

**Evidence limits.** I inspected captures and source, without running interactions. Keyboard focus restoration, native dialog/popover behavior, screen-reader announcements and the downloaded file were not exercised. Network loading and failure states are outside this bundled-data example.
